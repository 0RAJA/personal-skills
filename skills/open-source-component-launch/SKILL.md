# 开源组件从立项到首发

从项目当前阶段开始。只有缺失的前置条件会改变结论时，才回头补做。评估不意味着获准创建仓库或发布。

## 1. 先判断值不值得做

- 明确谁会调用、遇到什么问题、问题不解决有什么后果。选能区分方案的可观察场景，并写清哪些需求不做。如果还没有明确的调用方，建议先做限时验证，或暂缓做成独立包。
- 优先找官方方案或已经在用的方案。用同一组场景比较直接采用、写一层轻量适配或给上游贡献、独立自研。查现行官方文档；条件允许时，做一个足以区分方案的小实验。区分实测、文档说明和推测。
- 比较行为是否满足需求、接入和维护成本，以及相关兼容性和许可证限制。给出结论：直接采用、适配或贡献上游、自研，或暂缓。说清什么新证据会改变结论。只要现成方案能以合理成本满足硬性要求，就不必另建项目。
- 将工作代码对外发布前，确认权属、授权、上游声明和许可证，移除内部标识、生产数据和密钥。未确认可以公开前，保持私有。

## 2. 先验证关键行为，再搭基础设施

- 从用户真正会用的入口验证正常路径和后果最严重的失败场景。重点看失败后调用方实际观察到什么，不只看内部方法有没有执行。能用真实调用方就用；用替代方案时，说明替代了什么、哪些结论还不能下。
- 明确组件和宿主各自负责什么，以及最小公开 API 或 CLI 应承诺什么。只有其他调用方确实需要时，才把原项目的特有行为变成公开约定。

## 3. 准备首发：CI/CD 的三道检查

沿用仓库约定，能省事就复用生态里的模板。提供许可证和 README，说明适用场景、限制和能跑通的快速上手示例。平台和版本的测试范围，以及是否加额外检查，取决于文档对用户作出的承诺。

- **合入前**：跑项目常规检查和核心行为测试，覆盖后果最严重的失败场景。
- **发布前**：在源码目录之外的干净环境里，用用户将拿到的东西跑一遍快速上手。发布软件包时，直接用通过验证的产物，不要重新构建。适用时核对版本与 Git 标签是否一致。PR 检查不得接触发布凭据。
- **发布后**：获准发布后，从实际交付渠道验证。比如安装软件包、下载并运行 CLI，或在已发布的源码标签或提交上按文档操作。手动首发也可以，只要保留这些检查。

把发布准备与实际发布分开。不要默认有权创建公开仓库、更改可见性、发布产物或关闭相关事项。如果用 GitHub Actions 发布到 PyPI，再读 [Python 首发清单](references/python-pypi-release.md)。

## 4. 记录结论与交接

说明怎么选、为什么、做了哪些验证、还有哪些没做和没解决，以及下一步可逆的动作。如果新方案替代了旧工作，附上替代方案的链接，建议关闭过时的 PR 或 Issue，避免把重复代码合进去。扩充 CI、双语文档、演示、基准测试和迁移指南，按实际用户和兼容性承诺取舍。

比较工具或找实际案例时，读 [现成方案与案例](references/existing-options.md)。不要仅因某个第三方模板出现在清单里就安装或运行它。
