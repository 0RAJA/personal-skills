# 本地上下文维护

让材料的归属、当前状态和接续入口清楚。整理方式服从项目用途与既有风格，改动规模以解决实际问题为准。

## 1. 理解背景与风格

- 明确当前任务、材料用途、后续怎样查找和接续，以及项目根、可写范围和只读边界。已有信息足够就直接采用，只询问影响判断的重要缺口。
- 读适用的 `AGENTS.md`、项目说明、材料入口和相邻专题；从目录组织、命名、层级、索引和正文粒度识别已有风格。优先沿用，有缺口时再提出必要约定，不照搬示例布局。
- 先用 `rg --files --hidden` 定位，再读相关正文；已知 ignored 目录要显式指定并按需加 `--no-ignore`。没有总索引或映射时，按任务抽查，不先造台账或遍历全部日志、快照和依赖。
- 读相关整理记录，区分当前结论、历史过程、原始证据和待核实材料。用正文、代码与有效记录交叉判断；日期、mtime、文件名或同字节均不足以决定过期或去重。旧迁移目标变化时先追查后续去向，不重放旧清单。

## 2. 提出最小整理建议

说明问题、证据、建议动作及其对查找和接续的帮助。可补导航、修引用、调整层级、迁移或归档；是否合并正文取决于内容与来源角色，不能只看名称或日期。没有实际问题时保持原样。

归属不明、用途不清、规则冲突，或合并/归档/更换常用入口会影响使用时，向用户说明证据、建议和取舍。已有授权内的明确事项直接推进，不逐步强制确认；未决项保留，继续独立可做的部分。

沿用现有进展记录，简要列出受影响路径、依赖、预计改写/移动、冲突和验证方法。移动前实际检查旧新路径，给出预览；小修补无需另建计划文件。需要记录时可裁剪使用[维护记录](assets/maintenance-record.md)，判断示例见[虚构场景](references/project-examples.md)。

## 3. 在授权范围内执行

- 改动前记录涉及文件的内容哈希；使用 Git 时同时记录工作区和暂存区状态。留意 ignored 材料、软链接与共享 worktree，避免间接修改其他工作区。
- 临写前复核源内容和目标占用，先备份并校验改写原件。前提变化就重评或跳过，保留后续修改；不覆盖已占用的迁移目标，不用旧全文消解冲突。
- 脚本、样本和结果按依赖成组保留，修正受影响的入站引用、相对路径及运行位置约定。仅做所需静态检查，不执行历史排查/生产脚本，不批量改写原始日志或快照。
- 按实际粒度记录旧/新相对路径、前后哈希、备份及已执行/跳过/冲突状态。保留未知材料和未提交工作；删除、范围外写入、安装或公开内容另按授权处理。

恢复只撤销实际执行项：核对当前内容仍匹配改后哈希、备份匹配原哈希、旧路径未被占用，再按逆序恢复。存在后续变化时保存当前内容并标记冲突，不强行覆盖，也不把部分恢复说成全部完成。

## 4. 验证与交接

按当前场景检查：能否从约定入口找到材料、分清当前/历史/未决事项、知道下一步入口及所需证据。复核所有受影响的本地引用与路径依赖、原件去向和原有工作保护；链接存在不代表正文或业务验证通过，未检查的外链/锚点与范围应说明。

优先修订或复用现有入口，只有现有入口不能满足导航需要时才新增；仅将验证过的入口补入最近一层索引，避免重复维护当前状态。交付实际变化、保留/未决项、检查结果和备份位置；继续使用同一进展入口。再次整理只看新增或变化及其引用，没有新问题就不新增文件或重复迁移。
